# 自研检索引擎 spec（v1）

> 一个引擎，两个用途：**生成报告时取证据**（AI 不许自由发挥，只能从这个引擎的结果里挑）＋ **用户提问时检索**（外人不用读代码）。索引只建一次，两边复用——这也是"省 API"的另一半。

---

## 1. 索引对象（5 类，v1 只做前 4）

| 类型 | 粒度 | 从哪来 | 用途 |
|---|---|---|---|
| `file_chunk` | 60 行 / 10 行重叠 | 后缀白名单文件 | 兜底召回（代码、文档） |
| `symbol` | 函数/类/路由注册/命令/中间件 | 启发式解析（正则 + 缩进/括号） | 槽位 `entry` / `start_point` |
| `config_item` | 单条配置项 | `.env.example`、config 文件、常量块 | 槽位 `config` |
| `dep` | 单条依赖 | go.mod / package.json / requirements.txt | 槽位 `stack` / `integrations` |
| `rule_finding` | 单条规则命中 | 障碍规则引擎 | 槽位 `traps` |

每条记录必须带 `path + start_line + end_line`（**无行号的记录不许入库**，这是引用校验的地基）。

---

## 2. 字段与权重

```text
chunk(id, kind, path, start_line, end_line, text, symbols, imports, lang, bytes)
```

BM25 列权重（v1 调参起点，`make eval` 里再校准）：

| 列 | 权重 | 理由 |
|---|---|---|
| `path` | 1.5 | 文件名常直接命中意图（`middleware.go`、`deploy.sh`） |
| `symbols` | 1.3 | 函数名比正文更能回答问题 |
| `text` | 1.0 | 兜底 |

---

## 3. 召回管线

```text
query
 ├─0 意图分类（规则）：run | config | where | deps | trap | general
 ├─1 查询理解：中文 → 英关键词扩展（确定性术语表，可单测）
 ├─2 双通道召回（同一 FTS5 索引，unicode61）
 │    a) 严格通道：所有 token AND
 │    b) 宽松通道：任一 token OR
 ├─3 融合：RRF（Reciprocal Rank Fusion，k=60）
 ├─4 加权：路径命中 +0.012 / 符号命中 +0.010 / 意图先验（问"配置"优先 .env.example）+0.020
 └─5 输出契约
      {path, start, end, snippet, score, why}   -- 必带行号，可回查
```

**分词实现**（v1 不依赖 jieba / 任何模型）：
- 拉丁标识符：原词 + camelCase/snake_case 拆分（`GetUserByID` → `getuserbyid, get, user, by, id`）
- CJK：连续汉字串做 **二元切分**（`如何启动项目` → `如何/何启/启动/动项/项目`），≤4 字时额外保留整串
- 结果写入 `tok_text` 列，由 FTS5 直接索引；同样规则处理查询

> 为什么不用 trigram：实测（§4）2 字词（"部署"）在 trigram 下 0 命中；二元切分同时覆盖 2 字与 4 字场景，且完全确定、可单测。

**输出契约是硬约束**：任何一条结果都必须能回查原文并高亮，否则丢弃。

## 4. 实测基线（2026-10-28，`scripts/proto_index.py` 真跑）

索引 `ginstarter-temp`（Go 脚手架，43 文件 → 59 chunk）：

| 查询 | unicode61 | trigram | 结论 |
|---|---|---|---|
| `how to run server` | 2.5ms，Top1 `cmd/app.go#L51-L90` | 0.6ms | 英文召回可用，代码+README 都能命中 |
| `database migration` | 0.3ms，Top1 `readme.md#L51-L110` | 0.6ms | 路径/正文双命中 |
| `middleware auth` | 0.3ms，Top1 `internal/route/middleware.go` | 0.4ms | 符号级命中（文件名即答案） |
| `配置文件在哪` | **0 命中** | 0 命中 | 仓库全英文 → 中文 query 撞语义鸿沟 |
| `部署` | **0 命中** | 0 命中 | 同上 |

索引 `jyh`（Go+Vue，178 文件 → 386 chunk）：

| 查询 | unicode61 | trigram | 结论 |
|---|---|---|---|
| `部署` | 4 命中，Top1 `docs/项目设计架构文档.md` | **0 命中** | 双字词：unicode61 可行，trigram 不行（<3 字） |
| `如何启动项目` | **0 命中** | 0 命中 | **整串被当一个 token → 必须分词** |
| `数据库迁移` | 0 命中 | 4 命中，Top1 `README.md#L51-L110` | 四字词 trigram 可行 |

**三条硬结论（直接决定实现方式）**

1. **必须做中文分词**：否则"如何启动项目"这种整句 0 命中 → v1 用自研二元切分（不引入 jieba，零依赖、可单测）。
2. **单字/双字词与多字词需要不同处理**：trigram 对 2 字词失效（"部署" 0 命中）、unicode61 对长句失效 → 二元切分 + 整串保留同时覆盖。
3. **中文提问 × 英文代码 = 必然鸿沟**：必须加"中→英关键词扩展"层（确定性术语表 v1，LLM 扩展 v2）。

**v1 最终实现**：自研分词（标识符拆分 + CJK 二元切分）+ 单 FTS5 索引 + 严格/宽松双通道 + RRF + 路径/符号/意图先验加权。
`scripts/proto_index.py` 保留为原始实验记录（当时对比了 unicode61 vs trigram），是技术文档里"如何选型"的证据。

> 这三条是写进技术文档的**实测证据**，不是设计臆测——这正是"过程可复现"和"工程质量"两项分数的抓手。

## 5. 评测（`make eval`）

| 指标 | 方法 | 目标 |
|---|---|---|
| Recall@5 | 3 个仓库 × 20 条标注 query（人工标"哪几处是正解"，≤60 条） | ≥0.80 |
| MRR | 同上 | ≥0.65 |
| 引用回查率 | 所有返回结果的 path#Lx-Ly 可回查 | 100% |
| 端到端延迟 | index 后单查询 p95（本地） | ≤120ms |
| 中文 query 命中率 | 10 条纯中文问题 | ≥7/10 |

> 标注量 60 条是这份方案唯一的人工成本，且**一次标注长期复用**（换算法不改标注）。

## 6. 实现分期（对齐 21 天排期）

| 阶段 | 内容 | 日 |
|---|---|---|
| S1 | 自研分词 + FTS5 索引 + 严格/宽松双通道 + 输出契约 | D3–D5 |
| S2 | 符号索引 + 路径/符号 boost + 意图分类 + 中英扩展 | D6–D8 |
| S3 | RRF 融合调参 + （可选）向量召回 bge-m3 | D9–D11 |
| S4 | 生成侧接入：模板槽位 → 检索计划 → 证据包 | D9–D11 |

**如果时间不够**：砍 S3 的向量召回（RRF 用 a+b 两路），保留 S1/S2/S4/S5——实测表明 BM25 + 符号 boost 在代码仓库上已经够用。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 中文分词质量差（代码标识符混中文） | 分词前先按标识符边界切；标识符整体保留不切 |
| 大仓库索引慢/大 | 白名单 + 8KB + 40 文件上限；索引落 SQLite，可增量（按 path+mtime） |
| 用户问"为什么这个项目慢"这类不可检索的问题 | 意图分类拦下 → 明确回"报告未覆盖，建议看 X 槽位"，不硬编 |
| 向量模型拉取失败（评委机器） | 向量层做成可选开关 `ENABLE_VECTOR=0` 默认关 |
